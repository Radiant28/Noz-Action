# Исследование клиента: камера и захват цели прицелом

Дата: 4 ноября 2026 года.

**Вывод: в открытой IDA-базе найдены и проверены по коду необходимые функции для клиентского прототипа: постоянный обзор мышью, камера за спиной, прицел и штатный выбор противника под ним. Серверная доработка для такого выбора цели не требуется. Готовый патч EXE и работоспособность в игре этим исследованием не подтверждены.**

Речь о выборе обычной цели WoW по прицелу. Расчёт попадания и допустимости способностей остаётся серверным. Принудительный поворот камеры на врага и стрельба по частям тела в исследуемый прототип не входят.

## Объект исследования и границы проверки

- IDA MCP: открытая база `Wow_12340.exe`, исходный путь в метаданных `G:\Games\World of Warcraft\Wow_12340.exe`.
- База загрузки: `0x00400000`, x86. Адреса в отчётах — виртуальные адреса, не смещения внутри файла.
- MD5 из метаданных IDA: `45892bdedd0ad70aed4ccd22d9fb5984`. SHA-256 исходника IDA не предоставила. Метаданные базы не доказывают наличие неизменённого исходного файла по старому пути.
- Рабочий файл: `D:\Wow Nozdor\WoWNozdor\WoW.exe`, версия ресурса `3, 3, 5, 12340`, размер `7918096` байт.
- MD5 рабочего файла: `9a21e982d20f6b323cc9b84e09f116db`.
- SHA-256 рабочего файла: `c33f54116161b0baf3d6f3b58276688336e96c50a80e921f10a8d5a6c38a4a60`.

Исследование выполнено через read-only декомпиляцию, ассемблер, callers/xrefs и чтение байтов IDA. EXE не запускался, процесс игры не исследовался, база IDA не изменялась. Имена и типы в существующей базе проверялись по поведению: несколько аннотаций оказались ошибочными.

## Подтверждённая цепочка для прицела

1. Выполнять новую логику на штатном клиентском потоке, когда существует игрок и загружен мир.
2. Учитывать отдельно готовность матриц и списка моделей. В 0.2.2 исправлен прежний вывод: после OnWorldUpdate (`0x4FB036`) списки уже очищены и ещё не заполнены отрисовкой. Для штатного model picking прототип вызывает Tick до OnWorldUpdate через CALL `0x4FB031`, используя камеру и модели предыдущего отрисованного кадра. Матрица WorldToScreen обновляется в `0x4FAB37..0x4FAB67`, но её готовность сама по себе не делает model picking допустимым. См. `../client-prototype/target-pick-order-evidence.json`.
3. Для точного попадания прицелом переиспользовать screen-ray/model-pick chain. Она обрезает луч по геометрии мира, затем определяет модель на луче.
4. Проверить полученный GUID, тип объекта, возможность атаки, состояние жизни и нужную дальность. Известный клиенту объект не обязательно виден без препятствий.
5. Менять цель через Target только при необходимости, а не записывать GUID напрямую. Новая логика удержания и переключения должна работать с GUID и повторно разрешать объект перед использованием.
6. Для более мягкого захвата возле прицела использовать EnumVisibleObjects + world position + WorldToScreen + проверку препятствий. Размер зоны захвата и точку на теле модели нужно проверить в игре.

Точный screen pick и мягкий выбор возле прицела — два варианта реализации. Для первого прототипа достаточно точного screen pick; радиус помощи можно добавить после его проверки. Удержание цели, подавление лишних событий и правила ручного выбора — новый код, а не найденная готовая функция.

## Проверка рабочего EXE

Сохранены байты **49 полных диапазонов функций по границам IDA**, суммарно более 17 КБ. Скрипт сопоставил VA базы с RVA и физическими секциями PE рабочего EXE. **48 диапазонов совпали побайтно; один отличается.** Это проверка выбранных диапазонов, не всех вызываемых функций, глобальных данных, DLL и кода, который может изменяться при запуске.

Отличие внутри `CGGameUI::Target`:

- Функция начинается по `0x524BF0`; её проверенный диапазон — 965 байт.
- По `0x524DC1..0x524DCD` (смещение файла `0x1241C1..0x1241CD`) в рабочем EXE стоят 13 байт `90` (NOP).
- В IDA на этом месте находятся вызовы, подписанные OsGetAsyncTimeMs и CGUnit_C::UpdateSpellCastBars, с подготовкой аргументов.
- Остальная часть этого диапазона совпала. Нельзя считать функцию полностью тождественной базе или восстанавливать эти байты без отдельной задачи. Авторство и назначение прежнего патча не устанавливались.

Полный результат: [local-comparison.json](local-comparison.json). В [ida-code-ranges.json](ida-code-ranges.json) сохранены исходные байты сравнения из базы.

## Ошибки, которые нельзя переносить из аннотаций IDA в код

- `ClntObjMgrObjectPtr` штатные callers передают пять DWORD: GUID low/high, mask, source file, source line. Псевдокод показывает только GUID и mask.
- `0x6E6EF0`, подписанная SetPosition, фактически **читает** мировую позицию. `0x6E6F10`, подписанная GetPosition, читает сырые координаты без преобразования транспорта.
- `0x6020B0`: аргументы движения камеры — float dx/dy и необязательный указатель, несмотря на неверный прототип в базе.
- `0x5FE880`: thiscall(camera, rect*), а не указанный IDA stdcall.
- `0x5FE4E0` CreateViewFromCamera сохраняет настройки вида в CVar; матрицы строит другой код.
- `0x7FD620`, подписанная __uncaught_exception, проверяет pending spellCast, а не состояние C++ exception.
- `EnumVisibleObjects` перечисляет объекты, известные клиенту. Это не доказательство видимости через стены.
- Штатный Tab selector `0x524FC0` выбирает по направлению персонажа и циклически переключает список. Вызов каждый кадр не даст наведение по камере.

## Достаточность и оставшаяся работа

**Для проектирования и написания первого прототипа необходимых внутренних функций достаточно.** Не требуется менять протокол, боевую систему или писать отдельный renderer. Код можно разместить в EXE; внешний DLL-модуль не является обязательным способом исполнения.

Ещё не подтверждено или не реализовано:

- Безопасное конкретное перенаправление управления, сохранение регистров/flags/FPU, размещение нового кода и данных в PE, обработка повторного входа.
- Реальные ABI, последовательность кадров и корректность объектов/матриц в запущенном клиенте.
- Включение/выключение режима и освобождение курсора при меню, чате, Alt-Tab, логине/логауте, загрузке карты и /reload.
- Поведение на транспорте, в vehicle, при смерти, spectator/cinematic и смене управляемого юнита.
- Отрисовка/масштабирование прицела и мягкое удержание целей. Найдены примитивы, готового пользовательского режима в EXE нет.
- Маски коллизий, точки прицеливания и отличие видимости из камеры от видимости из персонажа. Клиентская LOS не заменяет серверную проверку заклинания.
- Боковое смещение камеры за плечо не подтверждено как штатная настройка. Найденный offset `+0x13C` действует вдоль up. Для запрошенной камеры **по центру за спиной** боковое смещение не обязательно.
- Совместимость существующих модулей и реакция античита сервера. Отсутствие отдельной DLL не делает патч невидимым.

Следующий практический этап: минимальный обратимый патч на отдельной копии клиента — переключение MouseLook и освобождение мыши. Затем диагностический прицел/показ GUID под центром, и только после проверки — автоматическая смена цели.

## Что создано и проверено

Все новые файлы находятся в `client-research`; существующие EXE, DLL, аддоны, настройки и IDB не изменены.

- `compare_ida_ranges.py`: только чтение PE и сравнение диапазонов, без запуска или модификации клиента. Стандартная библиотека Python, дополнительных зависимостей нет.
- Встроенный `--self-test`: синтетический PE32, проверка RVA/file mapping, отказ для виртуальных/выходящих за границы диапазонов и повреждённых заголовков.
- Проверены синтаксис Python, загрузка JSON-артефактов и фактическое сравнение рабочего EXE.
- Ruff/Bandit/MyPy в PATH не обнаружены; отдельный запуск этих инструментов не выполнялся.

Повторить проверку из корня проекта:

```powershell
python .\client-research\compare_ida_ranges.py --self-test
python .\client-research\compare_ida_ranges.py
```

Результат `match=false` — ожидаемое диагностическое наблюдение о текущем EXE, а не разрешение автоматически исправить файл.
